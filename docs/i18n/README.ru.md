## Обзор проекта

Агентные IDE вроде Orca и Paseo дают рабочую среду: параллельные worktree, отдельный терминал на
каждого агента, просмотр diff. Но как только на них ведёшь настоящий проект, всплывают одни и те же
проблемы.

История того, что уже было сделано, не сохраняется. Сессия заканчивается или работу подхватывает
другой агент, и прошлые решения исчезают. Приходится заново объяснять то, о чём уже договорились, а
иногда работа возвращается к подходу, от которого давно отказались.

Проверять результат тоже непросто. Поэтому нужно место, где человек проверяет работу и выпускает
её. Для блога это админ-страница, для мини-приложения Toss — предварительная проверка перед
отправкой и консоль.

Ни то, ни другое не решается шлифовкой промптов. На каждую точку, где всё ломается, мы поставили по
системе.

| Что ломается | Система | Чем обеспечивается |
| --- | --- | --- |
| Потеря контекста | Справочник · индекс wiki · кратко- и долгосрочная память загружаются в начале каждой сессии | Хук SessionStart |
| Дрейф качества | Шлюз публикации — детерминированная функция. Люди и агенты видят один и тот же вердикт | Внутри нет вызова LLM |
| Смешение ролей | Каждый агент объявляет рантайм, модель и область записи | `agents/registry.yaml` |
| Ресурсы без происхождения | Единственный путь генерации изображений, происхождение фиксируется у каждого ресурса | Страж инструментов + аудит |
| Случайная публикация | Агенты доходят до `in_review` и останавливаются. Кнопку нажимает человек | В типах такого пути нет |

## Установка

### Поручить агенту (рекомендуется)

Вставьте это как есть в тот кодовый агент, которым пользуетесь: Claude Code, Codex, Cursor, Gemini
CLI.

```text
Install Agent Company by following the instructions here:
https://raw.githubusercontent.com/TOKTOKHAN-DEV/agent-company/refs/heads/main/INSTALL.md
```

Руководство самодостаточно — от клонирования до проверки. Если текущая папка пуста, клонирование
идёт прямо в неё, а каждый обязательный и необязательный инструмент описан вместе с запасным
вариантом, так что агент сам разберётся там, где застрянет.

### Вручную

```bash
git clone https://github.com/TOKTOKHAN-DEV/agent-company.git
cd agent-company

pnpm install
pnpm company-setup    # проверка зависимостей → выбор компании → подготовка окружения → верификация
pnpm dev
```

Полную процедуру и разбор проблем смотрите в [INSTALL.md](../../INSTALL.md).

> Это `pnpm company-setup`, а не `pnpm setup`. `setup` — встроенная команда pnpm, поэтому скрипт с
> таким же именем окажется перекрыт.

## Ядро и шаблоны

Репозиторий состоит из двух слоёв. Ядро одинаково в любой компании, а что именно строится —
решает шаблон.

```
agent-company/
│
├── ── ядро (есть всегда) ───────────────────────────
│   ├── .claude/          хуки (SessionStart · PreToolUse) · слэш-команды
│   ├── wiki/             знания о проекте + кратко-/долгосрочная память + ADR
│   ├── agents/           место для состава (registry.yaml + <id>/)
│   ├── scripts/          детерминированные shell-скрипты
│   ├── CLAUDE.md         инструкции для Claude Code
│   └── AGENTS.md         общие инструкции для всех ИИ-агентов разработки
│
├── ── шаблоны (выбрать один и развернуть) ──────────
│   └── templates/<id>/
│       ├── template.yaml   манифест — скрипты · проверки · жёсткие правила · следующие шаги
│       └── files/          пути относительно корня репозитория (apps/ · packages/ · agents/ …)
│
└── ── продукт (только этот репозиторий) ────────────
    └── site/               лендинг. один статический HTML, без сборки → Vercel
```

`pnpm company-setup` предлагает выбрать шаблон, копирует `templates/<id>/files/` в корень, а затем
сливает `script:` из манифеста в корневой `package.json`. При смене шаблона отзываются ровно те
ключи скриптов, которые добавил предыдущий.

### Доступные шаблоны

| id | статус | что получается | состав | шлюз |
| --- | --- | --- | --- | --- |
| [`blog`](../../templates/blog/README.md) | stable | публичный сайт + стол проверки | blog-writer · image-maker | `audit` → `in_review` |
| `blank` | stable | только ядро. пустой состав | решаете сами | делаете сами |
| [`app-in-toss`](../../templates/app-in-toss/README.md) | preview | WebView мини-приложение Toss | spec-writer · ui-builder · release-manager | `preflight` → проверка в консоли |

```bash
pnpm template list                    # список · что применено
pnpm template apply <id>              # развернуть
pnpm template apply <id> --force      # перезаписать поверх другого шаблона
pnpm template prune                   # убрать неиспользуемый каталог и лендинг
```

`planned` означает, что в манифесте записано намерение, но содержимого ещё нет. `apply` откажется,
потому что развёрнутая пустая оболочка приведёт лишь к поискам, почему ничего не работает.

### Один проект — одна компания

Один репозиторий имеет два лица. После выбора остальной каталог и лендинг продукта в этом проекте
не нужны, поэтому `pnpm company-setup` предлагает их убрать.

| | Репозиторий продукта (этот) | Ваш проект, созданный через Use this template |
| --- | --- | --- |
| `site/` (лендинг) | есть → задеплоен на Vercel | удаляется при уборке |
| Невыбранные шаблоны | все на месте | удаляются при уборке |
| `files/` выбранного шаблона | есть | удаляется (уже лежит в корне) |
| `template.yaml` выбранного шаблона | есть | остаётся |
| Ядро | есть | есть |

Сохранить манифест принципиально важно, потому что `check-deps.sh` читает из него `verify-*`, а
`load-context.sh` читает `rule:`. Если его удалить, проверки и жёсткие правила исчезнут без единой
ошибки.

В репозитории продукта лежит маркер `.company/PRODUCT`, поэтому prune там откажется работать. Тот,
кто склонирует репозиторий и запустит настройку, каталог не потеряет.

Если позже понадобится другой шаблон, его можно забрать из upstream.

```bash
git remote add upstream https://github.com/TOKTOKHAN-DEV/agent-company.git
git fetch upstream && git checkout upstream/main -- templates/
```

### Почему шаблоны не вынесены в отдельные репозитории

Ключи манифеста развиваются вместе со скриптами ядра. Читаются они через `sed`, поэтому незнакомый
ключ молча игнорируется, и устаревший удалённый шаблон обрушил бы целые блоки проверок без единой
ошибки. Один репозиторий этого не допускает. К тому же сетевой запрос посреди установки нарушил бы
обещание, что два запуска дают одинаковое состояние.

Вес — слабый аргумент. С точки зрения git `templates/` занимает 388K.

Разделять стоит тогда, когда сторонние разработчики начнут присылать шаблоны, когда в шаблоне
появятся крупные ресурсы или когда циклы релизов разойдутся. Править придётся одно место —
копирование файлов в `template.sh`.

## Что даёт ядро

### 1. Слой контекста

В начале сессии хук подставляет следующее.

```
жёсткие правила ядра → текущая компания (шаблон) + её жёсткие правила → индекс wiki
                     → долгосрочная память → свежая краткосрочная память → состав → статус git
```

Загружается индекс, а не весь wiki. Модель получает карту и сама открывает то, что ей нужно
([ADR-0003](../../wiki/decisions/ADR-0003-session-context-loading.md)).

Двухуровневая память оставляет только то, что живёт долго.

```
краткосрочная ──(упомянута 3+ раза / по-прежнему верна)──▶ долгосрочная
долгосрочная  ──(становится правилом проекта)───────────▶ документ wiki или ADR
```

Повышением управляет `/save-memory`.

### 2. Состав

Агенты здесь — не субагенты Claude. Каждый представляет собой отдельный процесс в собственном
терминале, и рантаймы у них разные. Именно поэтому ADE вроде Orca может запускать их по-настоящему
параллельно.

```bash
pnpm agent --list
pnpm agent <id> "<задача>"
pnpm agent <id> "<задача>" --dry-run   # выводит только собранную команду (для другого терминала)
```

Лаунчер читает рантайм и модель из `agents/registry.yaml`, собирает `AGENT.md` и индекс скиллов
(создаётся сканированием папки) в системный промпт и запускает соответствующий CLI. Добавленный
скилл появляется без какой-либо регистрации.

Агента добавляют ради рантайма и параллельности, а не ради роли. Если существующий агент справится
с работой, лучше добавить скилл →
[wiki/05-agent-operations.md](../../wiki/05-agent-operations.md)

### 3. Шлюз публикации

Шлюз — детерминированная функция. Админ-экран и CLI вызывают одну и ту же функцию, поэтому люди и
агенты видят одинаковый вердикт. Внутри нет вызова модели, потому что модель, оценивающая
собственный результат, склоняется к одобрению.

Что именно проверяет шлюз, решает шаблон. Для `blog` это `pnpm audit:content`.

### 4. Политика изображений

Путь генерации изображений ровно один: Codex `imagegen`. Политика принадлежит ядру, а команда
приходит из шаблона, потому что куда попадает изображение и в каких метаданных фиксируется его
происхождение, зависит от предметной области. Для `blog` это выглядит так.

```bash
pnpm imagegen --slug <slug> --prompt "<описание сцены>"
```

Если Codex недоступен, откат идёт в таком порядке.

1. Продолжить без изображения (по умолчанию)
2. Попросить пользователя приложить своё (`source: user-upload`)
3. Поиск в вебе. Лицензию нужно проверить, а `source: web-search` и `license` записываются

Правило, живущее только в документе, не соблюдается, поэтому оно закреплено на трёх уровнях.

| Уровень | Механизм |
| --- | --- |
| Типы | В `ImageSource` нет значения `claude` |
| Хук | `PreToolUse` блокирует команды генерации изображений вне Codex |
| Аудит | Незаписанное происхождение или веб-изображение без лицензии считаются error → публикация невозможна |

Обоснование: [ADR-0002](../../wiki/decisions/ADR-0002-codex-only-image-generation.md)

### 5. Приём материалов

Забирайте то, что делалось в другом воркспейсе. Пригодится при переносе существующего
сервиса в мини-приложение, при получении дизайн-кита или когда подхватываете
недоделанный проект.

```bash
pnpm intake ~/Downloads/design-kit.zip
pnpm intake ~/work/other-repo --as reference
```

Команда распаковывает zip · tar.gz · папку в `inbox/<имя>/`, вычищает вроде
`node_modules` и **пишет оглавление (`INVENTORY.md`)** — стек, какие документы читать
первыми, изображения с их разрешением, дизайн-файлы, которые не открыть, и
предупреждение, если внутри похоже оказались ключи.

Оглавление нужно ради контекста. Дайте агенту папку целиком — и он сожжёт контекст,
открывая файлы по одному. Скажите, что где лежит, и он откроет только нужное.

Ничего из полученного не запускается. Симлинки удаляются (они могут указывать за пределы
репозитория), распакованный код никогда не устанавливается и не собирается. Присланный
zip — это материал для чтения, а не то, что нужно запускать.

`inbox/` не под контролем версий. **Это сырьё, а не результат** — в репозитории остаются
только извлечённые оттуда спецификации и ассеты (жёсткое правило ядра 3).

## Жёсткие правила ядра

Верны независимо от шаблона. Чтобы изменить любое из них, сначала нужно написать ADR в
`wiki/decisions/`.

1. **Единственный путь генерации изображений.** Ни другая модель изображений, ни SVG вместо неё.
2. **Кнопку публикации нажимает человек.** Агенты доходят до `in_review` и останавливаются.
3. **Истина — в файлах репозитория.** Результаты и решения версионируются в том же репозитории, что и код.
4. **Шлюз детерминирован.** Никакого вывода модели внутри проверки.
5. **Контекст загружается сам.** Никому не нужно помнить о том, чтобы его принести.

Правила предметной области записываются в `rule:` внутри `templates/<id>/template.yaml` и
подставляются поверх этих пяти в начале сессии.

## Команды

### Ядро (всегда)

| Команда | Описание |
| --- | --- |
| `pnpm company-setup` | Проверка зависимостей → выбор шаблона → подготовка окружения → верификация (+ по желанию: подписка/звезда на GitHub) |
| `pnpm check` | Только проверяет состояние (ничего не устанавливает), включая проверки текущего шаблона |
| `pnpm template list \| apply <id> \| prune` | Просмотр · применение · уборка шаблонов |
| `pnpm agent --list \| <id> "<задача>"` | Список · запуск агентов |
| `pnpm intake <zip \| папка>` | Забрать работу из другого воркспейса в `inbox/` и составить оглавление |
| `pnpm context` | Вывести контекст сессии вручную |
| `pnpm memory:new <topic>` | Создать файл памяти (`--long` для долгосрочной) |
| `pnpm dev \| build \| typecheck \| lint \| test` | Всё рабочее пространство (turbo) |

### Что добавляет шаблон

Применение `blog` добавляет `dev:web` · `dev:admin` · `audit:content` · `cover` ·
`imagegen`. Какие ключи придут, написано в строках `script:` манифеста.

## Слэш-команды

| Команда | Что делает |
| --- | --- |
| `/company-setup` | Полная проверка зависимостей + установка · выбор шаблона (подписка/звезда по желанию) |
| `/save-memory` | Сохраняет сессию в краткосрочную память и при необходимости повышает до долгосрочной/wiki |
| `/create-agent` | Создаёт агента сразу в registry + AGENT.md + skills/ |

Скиллы, которые читают агенты (`agents/<id>/skills/`), — это другое. Там лежат нейтральные к
рантайму плейбуки, которые лаунчер подставляет в системный промпт, поэтому их читают и агенты
codex.

## Как написать новый шаблон

```
templates/<id>/
├── template.yaml    манифест
└── files/           пути относительно корня репозитория
```

Манифест использует формат с повторяющимися ключами. YAML-парсер не подключается: его читают
`sed`/`awk`, потому что установка должна оставаться детерминированной.

| Ключ | Значение |
| --- | --- |
| `id` · `name` · `status` · `summary` | То, что видно в списке. `status` — `stable` · `preview` · `planned` |
| `ships` · `hires` · `gate` | Однострочные сводки (используются в документации и на лендинге) |
| `script: key=value` | Сливается в корневой `package.json`. При смене отзываются только эти ключи |
| `verify-workspace:` | Проверяет вплоть до связывания зависимостей (иначе ошибка) |
| `verify-dir:` | Наличие каталога + число файлов (иначе ошибка) |
| `verify-optional:` | Желательный файл/каталог (предупреждение, если отсутствует) |
| `verify-env: VAR=причина` | Проверяет значение в `.env`. Если не задано, сообщает, что отключено |
| `note-env: VAR=причина` | Значения, которые обычно пусты. Показывает только состояние |
| `runtime:` | CLI, которые использует этот шаблон (предупреждение, если их нет) |
| `mcp: имя=причина` | MCP-серверы, которые использует этот шаблон. Проверяется регистрация |
| `mcp-claude:` · `mcp-codex:` | Команда регистрации, выводимая при отсутствии сервера |
| `rule:` | Жёсткие правила этой компании, подставляемые поверх правил ядра |
| `next:` | Подсказки после установки. `${VAR}` подставляется из `.env` |

Манифест читают четыре скрипта: `scripts/template.sh` · `scripts/check-deps.sh` ·
`scripts/load-context.sh` · `scripts/company-setup.sh`. Если добавляете ключ, один из них должен
научиться его читать: ключ, который никто не читает, — это документация, а не конфигурация.

Регистрация MCP проверяется чтением конфигурационных файлов (`~/.claude.json` · `.mcp.json` ·
`~/.codex/config.toml`), а не запуском `claude mcp list`. Эта команда делает health check по сети,
что лишило бы `pnpm check` детерминированности.
