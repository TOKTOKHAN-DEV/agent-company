# 도구는 이름이 아니라 부작용으로 판단한다

**"출고는 사람만"(코어 하드 룰 2)을 도구 이름으로 적용하면 뚫린다.** 무엇을 부르지 않을지는
이름이 아니라 **그 호출이 바깥에 무슨 일을 일으키는가**로 정한다.

## 이 규칙이 나온 경위

앱인토스 콘솔 MCP 를 붙이면서 확인한 것.

| 도구 | 이름이 말하는 것 | 실제로 하는 것 | 판정 |
| --- | --- | --- | --- |
| `miniapp_update_icon` | 로고를 바꾼다 | **앱정보 검토 요청이 함께 나간다** (콘솔 웹의 "검토 요청" 버튼과 같은 호출) | 금지 |
| `miniapp_update_screenshots` | 스크린샷을 바꾼다 | 같음 | 금지 |
| `image_upload_url` + `PUT` | 업로드 URL 을 발급한다 | CDN 에 바이트를 올릴 뿐, 아무것도 신청하지 않는다 | 허용 |

`update_` 로 시작한다고 setter 가 아니고, `upload` 라고 위험한 것도 아니다. 셋 다 이름만
보면 정반대로 갈렸다.

## 판단 기준

부르기 전에 이 셋을 본다.

1. **사람에게 나가는가** — 알림 · 메일 · 게시 · 심사 신청
2. **돈이 움직이는가** — 충전 · 결제 · 판매 상태 변경
3. **되돌리는 데 사람이 필요한가** — 반려되면 영업일 3일을 다시 기다리는 종류

하나라도 참이면 **에이전트는 페이로드까지 만들어 두고 멈춘다.** 사람이 누른다.

## 그어야 하는 선

```
바이트를 올리는 것 ───── 에이전트
버튼을 누르는 것 ────── 사람
```

준비를 못 하게 막는 것이 목적이 아니다. 준비는 끝까지 하되 **마지막 한 번의 클릭**만
사람에게 남긴다. 그래야 사람이 확인할 것이 "무엇을 승인하는가" 하나로 줄어든다.

## 왜 이름을 믿으면 안 되는가

도구 이름은 만든 쪽의 관점이다. 콘솔 팀에게 `miniapp_update_icon` 은 "로고 필드를 갱신하는
엔드포인트"가 맞다 — 그쪽 도메인에서는 검토 요청이 갱신 절차의 일부이기 때문이다.
**부작용은 도구 설명 본문에 적혀 있다.** 이름만 보고 부르면 "설정만 바꿨습니다" 라고
보고하게 되고, 그건 사실이 아니게 된다.

새 MCP 를 붙일 때는 **도구 설명을 끝까지 읽고** 금지 목록을 먼저 만든다.

## 어디에 적혀 있나

규칙은 문서로만 두지 않는다.

- `agents/<id>/AGENT.md` 의 "절대 하지 않는 것"
- `agents/registry.yaml` 의 `hard_rules`
- `templates/<id>/template.yaml` 의 `rule:` (세션 시작마다 주입)
- 해당 스킬의 "부르지 않는 도구" 표
